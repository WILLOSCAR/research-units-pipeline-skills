# Generic archetypes

Use these when no domain pack matches the Success Spec's scope. They are
prompts for thinking, not mandatory categories; keep the ones the core set
populates and the spec asks about.

## Common chapter archetypes

- **Foundations / problem formulation** — when the field has competing
  task definitions, interfaces, or assumptions.
- **Core methods / components** — when the main reader question is how
  systems are built or which mechanism changes matter.
- **Learning / adaptation / coordination** — when systems improve over
  time, optimise policies, or coordinate several actors or components.
- **Evaluation / benchmarks** — when comparability, metrics, and protocol
  choices are major sources of disagreement.
- **Safety / robustness / governance** — when risk surfaces are
  substantive, not a short caveat.
- **Applications / deployment settings** — only if application differences
  meaningfully reorganise the literature.

## How to use them

Pick three to six that the abstracts populate, name each in the field's own
terms (not the archetype label), split each into two to four leaves the
papers actually fill, and write definitions per `taxonomy_principles.md`.
An archetype that would hold one paper is a comparison axis, not a node.
